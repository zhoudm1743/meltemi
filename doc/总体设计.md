# Meltemi 总体设计

项目名：Meltemi。Go module：`github.com/zhoudm1743/meltemi`。

## 1. 项目定位

本项目是一个使用 Go 开发的跨平台桌面 UI 库。它借鉴 Fyne 的跨平台窗口与自绘控件思路，以及 HTML/CSS 在结构和样式分离方面的开发体验，但不使用 Fyne 作为底层依赖，也不嵌入 WebView、浏览器引擎或 JavaScript 运行时。

这里的“原生”是指：

- 应用直接创建操作系统窗口，处理原生输入和桌面能力。
- 窗口内控件由本库布局并绘制，不以 Win32、Cocoa 或 GTK 的系统控件作为主要组件实现。
- 菜单、托盘、文件对话框等能力可以通过操作系统接口实现。
- 允许通过 cgo 使用 GLFW、OpenGL 等底层 C 库。

项目首先要解决的不是“能否画出控件”，而是 Go 桌面 UI 的开发体验：组件创建繁琐、样式难复用、界面代码样板过多。

## 2. 已确定的决策

- 使用 Go 作为公共 API 和主要实现语言。
- 面向桌面平台，Linux 优先，设计上支持 Windows 和 macOS。
- 不使用 Fyne 作为底部依赖。
- 不使用 HTML、JavaScript 或 WebView 实现界面。
- 允许通过 cgo 使用 GLFW、OpenGL 等底层库。
- 采用符合 Go 使用习惯的链式、声明式组件 API。
- 支持从外部文件加载 CSS 风格样式，但不要求兼容完整 CSS。
- 支持多窗口、托盘图标和菜单栏。
- 关闭窗口、退出应用、驻留托盘等行为由应用开发者配置，库不强制绑定一种生命周期。
- 可视化设计器属于后期能力，不进入首版范围。

## 3. 目标

### 3.1 开发体验

- 用少量、可读的 Go 代码描述组件树、布局和事件。
- 支持通过函数拆分界面和组合自定义组件。
- 使用稳定类型和编译检查，避免以运行时字符串替代所有组件结构。
- 将颜色、字体、边框等外观从业务代码中分离。
- 为组件提供稳定的 ID、class 和状态，以便设置样式和编写测试。

### 3.2 桌面能力

- 一个应用可以创建、显示、隐藏和销毁多个窗口。
- 支持应用级事件循环和明确的退出机制。
- 支持窗口菜单、应用菜单、托盘图标及托盘菜单。
- 支持应用关闭最后一个窗口后退出或继续运行，并支持托盘恢复窗口。
- 对平台不支持的桌面能力返回明确错误或能力状态，不静默假装成功。

### 3.3 可维护性

- 公共 API 不暴露 GLFW、OpenGL 或某个操作系统的内部类型。
- 窗口后端、渲染器、文本和平台服务之间保持清晰边界。
- 平台差异集中在带构建约束的适配层中，不散落在组件代码中。
- 不为追求“一次编写，所有平台表现完全一致”而掩盖平台差异。

## 4. 非目标与反目标

首版不包含以下能力：

- Web、移动端、WebView 或 JavaScript 支持。
- 完整 HTML、CSS 或浏览器布局引擎。
- 可视化界面设计器。
- 完整复刻 Fyne 的组件和 API。
- 同时完成所有桌面平台的全部功能。
- 完整动画系统、复杂富文本、表格和高级数据可视化。
- 在首版实现全部输入法、无障碍和复杂文本能力。

需要避免的设计：

- 名义上独立，实际通过隐藏封装依赖 Fyne。
- 把样式系统不断扩展成浏览器引擎。
- 在公共 API 中泄漏后端类型，导致以后无法替换后端。
- 将关闭最后一个窗口固定为退出或固定为驻留托盘。
- 为追求简单而让 UI 组件默认支持任意 goroutine 并发访问。
- 无变化时持续满帧重绘，造成不必要的 CPU 和 GPU 占用。

## 5. 总体架构

```text
应用开发者
    │
    ▼
链式 Go API：App / Window / Component / Menu / Tray
    │
    ├── 组件与布局：组件树、测量、排列、焦点、事件分发
    ├── 样式系统：主题、样式表、选择器、状态、优先级
    ├── 数据绑定：值读取、值更新、变更通知
    │
    ▼
Canvas 与渲染抽象
    │
    ├── OpenGL Renderer
    ├── 文本与字体抽象
    │
    ▼
窗口与输入后端：GLFW
    │
    ▼
Linux / Windows / macOS

平台服务独立接入：
Linux：StatusNotifierItem / AppIndicator 等
Windows：Win32 菜单、托盘和系统接口
macOS：Cocoa 菜单、状态栏和系统接口
```

### 5.1 App

`App` 是应用级资源的拥有者，负责：

- 初始化后端并运行唯一的主事件循环。
- 管理所有窗口、应用菜单、托盘和全局样式。
- 接收其他 goroutine 投递的 UI 任务。
- 执行有序退出并释放窗口、渲染和平台资源。
- 提供桌面能力查询，避免应用假设所有平台都支持托盘或特定菜单行为。

`app.Run()` 每个应用进程只运行一次。窗口不各自运行事件循环。

### 5.2 Window

`Window` 表示一个独立顶层窗口，至少提供：

- 标题、逻辑尺寸、最小尺寸和图标。
- 内容组件、窗口菜单和窗口级事件。
- `Show()`、`Hide()`、`Close()` 等生命周期操作。
- 关闭请求、获得焦点、失去焦点和尺寸变化通知。

在 `app.Run()` 前调用的窗口操作可以进入待执行队列，运行后统一交给后端处理。

### 5.3 组件树与布局

采用保留组件树模型。链式 API 构建组件树，布局系统执行测量和排列，渲染器绘制最终结果。

首版布局建议包括：

- `Column`：垂直排列。
- `Row`：水平排列。
- `Stack`：层叠排列。
- `Scroll`：为内容提供滚动视口。
- `Spacer`：处理可伸缩空白。

首版基础组件建议包括：

- `Label`。
- `Button`。
- `Input` 和 `Password`。
- `Checkbox`。
- `Image`。

阶段 1 的 `Input` 和 `Password` 仅承诺单行输入，包括 UTF-8 文本插入和删除、键盘与鼠标定位光标、左右移动、Home/End、文本选择以及复制、剪切和粘贴。多行文本域、撤销/重做放入阶段 2；中文输入法和复杂文本整形仍在阶段 2 完成，不作为阶段 1 的隐含交付物。

List、Table、Tree 等复杂虚拟化组件放在后续阶段，避免首版同时解决过多状态、滚动和性能问题。

### 5.4 程序更新与自定义组件

首版使用组件方法主动更新界面，例如 `SetText()`、`SetValue()`、`SetEnabled()` 和 `SetVisible()`。方法更新组件状态并触发布局或绘制失效；对绑定输入值调用 `SetValue()` 时，同时更新绑定值和组件显示。

直接修改绑定指针对应的变量不会产生自动通知，应用需要调用组件的 `SetValue()`。首版不承诺通用响应式绑定框架。所有更新方法仍只能在 UI 线程调用，工作 goroutine 必须通过 `app.Post()` 更新。

首版的自定义组件仅承诺通过普通 Go 函数组合内置组件，不公开 `Measure`、`Arrange`、`Paint` 或任意 Canvas 绘制接口。内部扩展点应保持边界清晰，待组件契约稳定后再公开自定义布局和绘制 API，避免首版过早冻结底层接口。

### 5.5 后端边界

内部后端至少划分为三类能力：

- 窗口后端：窗口、事件、光标、剪贴板和高分辨率信息。
- 渲染后端：绘制图元、文字、图片和离屏资源。
- 平台服务：托盘、系统菜单、通知和文件对话框。

首版可以只有 GLFW + OpenGL 实现，但组件和样式系统不得直接调用 GLFW 或 OpenGL。后端接口应保持精简，不预先抽象尚未验证的移动端或浏览器能力。

## 6. Go API 设计方向

以下代码用于表达 API 风格，不是冻结的函数签名：

```go
app := ui.New()

if err := app.LoadStyles("app.css"); err != nil {
    log.Fatal(err)
}

account := ""
password := ""

loginWindow := app.Window("登录").
    Size(360, 240).
    Content(
        ui.Column(
            ui.Input(&account).
                Class("field").
                Placeholder("账号"),

            ui.Password(&password).
                Class("field").
                Placeholder("密码"),

            ui.Button("登录").
                ID("login").
                OnClick(func() {
                    login(account, password)
                }),
        ).Gap(12).Padding(20),
    )

loginWindow.Show()
app.Run()
```

设计原则：

- Go 代码负责组件结构、主要布局、数据和事件。
- 组件使用构造函数创建，常用配置可以链式调用。
- 复杂界面通过普通 Go 函数和自定义组件拆分，不鼓励无限深的链式嵌套。
- ID 用于标识窗口内的唯一组件，class 用于复用一组样式。
- 事件处理直接使用 Go 函数，不使用 JavaScript 或字符串脚本。
- 加载文件、创建平台资源等可能失败的操作应能返回错误。

## 7. 样式系统

### 7.1 定位

样式文件采用 CSS 风格语法，但只实现桌面 UI 所需子集。样式表不是 HTML 的配套技术，也不要求符合浏览器完整行为。

首版支持：

- 组件类型选择器，如 `Button`、`Input`。
- class 选择器，如 `.field`。
- ID 选择器，如 `#login`。
- 状态选择器：`:hover`、`:focus`、`:disabled`、`:checked`、`:pressed`。
- 颜色、字体、字号、背景、边框、圆角、透明度。
- 内外边距以及可覆盖的宽高等基础尺寸。
- 应用级默认主题和外部样式表。

首版明确不支持：

- JavaScript 表达式或行为。
- 完整 CSS 盒模型和浏览器布局。
- 复杂选择器、媒体查询和完整层叠规则。
- `!important`。
- CSS 动画和完整过渡系统。

### 7.2 示例

```css
.field {
    padding: 8px;
    border: 1px solid #cccccc;
    border-radius: 4px;
}

#login {
    background: #3478f6;
    color: white;
    border-radius: 6px;
}

#login:hover {
    background: #2968d8;
}

#login:disabled {
    opacity: 0.5;
}
```

样式中的 `px` 按逻辑单位解释，不代表物理像素；后端根据窗口缩放比例转换为实际渲染像素。

### 7.3 优先级

为避免样式结果难以预测，首版采用简化优先级：

```text
代码显式设置
> ID + 状态
> ID
> class + 状态
> class
> 类型 + 状态
> 类型
> 默认主题
```

同优先级规则按样式表中的出现顺序处理，后者覆盖前者。仅字体、文字颜色等明确标记的属性允许向子组件继承。

代码负责结构布局，样式负责可覆盖外观。`Gap()`、`Padding()` 等代码显式配置优先于样式表，防止主题意外破坏应用布局。

### 7.4 原生平台服务的外观

系统绘制的菜单、托盘菜单和文件对话框不接受本库 CSS。自绘菜单可以使用本库样式，但必须与系统菜单的能力差异一起写入文档。

## 8. 多窗口与生命周期

生命周期必须可由应用开发者控制。

### 8.1 窗口关闭

每个窗口支持配置关闭请求的行为：

- 销毁窗口。
- 隐藏窗口，保留组件树和状态。
- 交给应用回调决定，并允许取消关闭。

默认行为建议为销毁窗口，这是本设计的选择，不是使用方强加的需求。

### 8.2 最后一个窗口关闭

应用可以配置：

- 最后一个可见窗口关闭后退出。
- 保持应用运行，等待托盘或其他入口重新创建、显示窗口。
- 调用应用回调，由应用自行决定。

普通应用的默认行为建议为退出；驻留托盘的应用可以显式改为保持运行。

### 8.3 托盘驻留

没有可见窗口不应自动等价于退出。只要应用配置为保持运行，托盘菜单应能显示已有窗口或创建新窗口。`app.Quit()` 提供明确、可重复调用的退出入口。

## 9. 菜单与托盘

### 9.1 菜单模型

使用统一的跨平台菜单描述，支持：

- 普通菜单项和子菜单。
- 分隔线。
- 启用、禁用和选中状态。
- 快捷键描述和实际按键分发，不只是显示快捷键文本。
- Go 事件回调。

后端负责将菜单映射到合适的平台形式：

- macOS 可以映射为应用全局菜单。
- Windows 可以映射为窗口菜单。
- Linux 首版明确采用窗口内自绘菜单栏和菜单弹出层，不依赖 GTK 或特定桌面菜单协议。

因此，阶段 1 需要统一的 Overlay/Popup 层，支持子菜单弹出、层叠绘制、指针捕获、焦点转移、点击外部关闭和 Esc 关闭。该层后续也可复用于下拉框、提示框和上下文菜单。

不同平台的位置和外观允许不同，应用不应依赖像素级一致。

### 9.2 托盘模型

托盘至少支持图标、提示文本、菜单和明确销毁操作。托盘是否可用通过能力查询或错误返回体现。

Linux 优先评估 StatusNotifierItem/AppIndicator。GNOME、KDE 及其他桌面环境的支持情况不同，不能把“Linux 后端已实现”直接视为所有桌面环境都能显示托盘。

## 10. 线程与事件模型

- 主事件循环运行在固定的操作系统线程上，使用 `runtime.LockOSThread` 等机制满足后端要求。
- 所有 UI 回调默认在 UI 线程执行。
- 组件、窗口和样式对象默认不是并发安全的。
- 其他 goroutine 通过 `app.Post(func())` 等机制请求在 UI 线程更新界面。
- 耗时业务操作应放在工作 goroutine 中，避免阻塞事件循环。
- 后端事件统一转换为库自己的事件类型，组件不接收 GLFW 事件。
- 输入系统需要处理命中测试、焦点、键盘导航和指针捕获。

首版的指针绑定便捷 API 由 UI 线程读写绑定值。应用在其他 goroutine 共享这些值时必须自行同步；后续可以增加带同步和变更通知的通用绑定类型。

首版键盘交互按以下规则实现：

- Tab 和 Shift+Tab 按组件树顺序在可聚焦组件间前后移动，暂不提供任意焦点跳转 API。
- Enter 激活当前聚焦按钮；窗口默认按钮和表单提交属于后续扩展。
- Esc 优先关闭最上层菜单或弹出层；没有弹出层时只向窗口发送取消事件，不擅自关闭窗口。
- 按键先交给聚焦组件处理，未消费的按键再向祖先、窗口菜单和窗口分发。
- 菜单快捷键使用统一的修饰键和按键描述，未消费快捷键最终可以触发对应菜单项。

## 11. 渲染与文本

### 11.1 渲染

- 首版使用 OpenGL 实现矩形、文字、图片、裁剪和基础圆角绘制。
- 推荐以 OpenGL 3.3 作为初始兼容性基线，具体版本在实现验证后确定。
- 组件树变化、窗口尺寸变化或样式变化时标记界面失效。
- 首版可以在失效后重绘整个窗口，后续再增加脏区域和增量渲染。
- 没有界面变化时不持续重绘。
- 阶段 2 已实现每 renderer 有界文本覆盖纹理 LRU（容量 256，key 为 Face 指针 + 文本 + 物理缩放，颜色每帧 uniform），仅在 owning context current 时执行 GL 删除；冷/热基准与计数器证据见 `doc/兼容性.md`。

### 11.2 文本

文本独立为子系统，不混入按钮等单个组件。需要逐步支持：

- 字体加载、字号和缓存。
- UTF-8 文本测量和换行。
- 阶段 1 的单行输入框光标、选择和基础剪贴板；多行编辑及撤销/重做在阶段 2 实现。
- 高分辨率下的清晰渲染。
- 复杂文本整形、双向文本和中文及其他语言输入法。

FreeType、HarfBuzz 等可以作为实现候选，但具体依赖由实现阶段验证后决定。技术验证可以先使用简单文本实现；在宣称适合正式桌面应用之前，输入法和复杂文本不能永久停留在非目标中。

阶段 2 现状（证据等级与限制见 `doc/兼容性.md`）：多行编辑/撤销/重做、HarfBuzz 整形、
RTL 显示与 caret、组合符与连字已在 DDE/X11 实测通过；边界为 strong-run 简化 bidi、
UAX#29 声明子集、灰度 emoji（彩色未支持）、fontconfig 未做字体质量排序；Fcitx 5 实测通过，
`meltemi-ime --smoke` 曾在阶段 2 验收时发现跨阶段失败（最后窗口 Hide 触发退出策略变更），已按
   smoke 配置修复（`--smoke` 下设 `LastWindowKeepRunning` 并于完成后退出，普通演示不受影响），
   完整 PASS、exit 0；诊断保留于 `doc/兼容性.md` 限制 1。

## 12. 平台策略

| 能力 | 共同抽象 | 平台适配方向 |
| --- | --- | --- |
| 窗口和输入 | WindowDriver | GLFW |
| 绘制 | Renderer | OpenGL |
| 菜单 | Menu / MenuItem | 系统菜单或自绘菜单 |
| 托盘 | Tray | Linux 桌面协议、Win32、Cocoa |
| 文件对话框 | Dialog 服务 | 各平台系统接口 |
| 字体与输入法 | Text / InputMethod | 公共文本栈加平台适配 |

Linux 首版不得写死 X11 专有假设。具体发行版、桌面环境、X11/Wayland 和显卡驱动支持矩阵在开发计划与验收环境中明确；平台服务要为能力缺失提供降级或错误。

阶段 2 唯一定稿的支持矩阵为 `doc/兼容性.md`，按自动化/协议 smoke/视觉/未验证分级；GNOME、KDE、Wayland、其他 IME、Windows、macOS 均为未验证，不得以 Linux 实现推断通过。

Windows 和 macOS 功能可以晚于 Linux 完成，但公共 API、线程模型和资源生命周期必须从一开始考虑这些平台，尤其是 macOS 的主线程与应用菜单要求。

## 13. 分阶段交付

### 阶段 0：技术验证

- 创建并管理两个 GLFW 窗口。
- 使用 OpenGL 绘制基础图元和文字。
- 验证鼠标、键盘、焦点和高分辨率信息。
- 验证主线程事件循环与跨 goroutine 投递。

### 阶段 1：Linux 最小可用版本

- `App`、`Window` 和组件树。
- Column、Row、Stack、Scroll 等基础布局。
- Label、Button、Input、Password、Checkbox、Image。

## 14. 验收方向

首个 Linux 最小可用版本至少应证明：

1. 登录示例可以用简洁的链式 Go API 编写，没有 Fyne 或 WebView 依赖。
2. 外部样式可以统一修改输入框和按钮外观，代码显式配置具有明确优先级。
3. 一个应用可以打开多个窗口，并正确处理显示、隐藏、关闭和退出。
4. 应用可以按配置在最后一个窗口关闭后退出或继续驻留托盘。
5. 菜单和托盘不可用时有明确反馈，托盘可以恢复窗口。
6. UI 回调与跨 goroutine 更新遵守统一线程模型。
7. 组件和样式代码不直接依赖 GLFW/OpenGL 类型。
8. 应用可以通过组件 Set 方法更新标签和输入值，工作 goroutine 可以通过 `app.Post()` 安全刷新 UI。
9. 单行输入可以完成光标移动、文本选择和复制粘贴，菜单快捷键和 Esc 关闭弹出层行为符合设计。

## 15. 测试与验证支撑

测试能力作为后端边界的一部分设计，不在实现完成后再补：

- 样式解析、优先级、布局、事件分发、数据更新和生命周期使用不依赖 cgo 的单元测试。
- 提供假窗口后端和记录绘制指令的假渲染器，使组件测试可以在无显示器的 CI 环境运行。
- GLFW/OpenGL 集成测试在可控的 Linux 图形环境运行；X11 环境可以使用 Xvfb，但不能用 Xvfb 结果替代真实桌面验收。
- 托盘、系统集成交互、输入法和高分辨率需要在真实桌面环境验证。
- 像素截图比较只用于受控环境，不要求不同 GPU 和字体环境产生完全一致的图片。
- 核心 Go 状态管理使用竞态检测，验证跨 goroutine 投递不会直接并发访问 UI 对象。

## 16. 留给实现阶段决定的事项

以下事项可以在不改变产品方向的情况下由实现者决定：

- 项目名、Go module 路径和最终包布局。
- Go 及第三方依赖的具体版本。
- GLFW Go 绑定的选择，以及 C 库的构建和分发方式。
- 公共 API 的最终函数签名和错误类型。
- OpenGL 的最终兼容版本和具体绘制算法。
- 字体、文本整形和输入法依赖的具体选型。
- Linux 首轮正式支持的发行版、桌面环境和显示协议组合。
- 是否需要为复用的第三方代码保留许可证和版权声明；若复用，则必须遵守对应许可证。

这些实现选择不得反过来引入 Fyne、WebView 或对某一操作系统的公共 API 依赖。
